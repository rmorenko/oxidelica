# Архитектурный анализ: путь к полной поддержке языка и MSL

Дата: 2026-08-24. Точка отсчёта: MSL 4.1.0, 767 примеров, из них
**400 флэттенятся и 80 запускаются**; из тех, что написаны для запуска, —
**640 runnable, из них 313 флэттенятся и 77 запускаются**
(`oxidelica library check`). Цель документа: честный реестр того, что
мешает остальным, сравнение с двумя референсными реализациями
(OpenModelica и rumoca), и план устранения с приоритетами.

Английская версия: [ANALYSIS.md](ANALYSIS.md).

---

## 1. Как устроена oxidelica сегодня

Четыре crate, ~52 500 строк, ноль внешних зависимостей:

```text
oxidelica-parser (~20 000 строк)
  lexer.rs                — токены
  parser/                 — рекурсивный спуск: classes, declarations,
                            equations, expressions, statements
  ast.rs                  — одно дерево на всё: Expr (24 варианта),
                            Component, EquationItem, ClassDef
  flatten/                — ОДИН проход, который делает всё:
    instantiate.rs (3648) — инстанцирование, extends, модификаторы,
                            redeclare, inner/outer, условные компоненты
    clocks.rs      (2514) — клокованные разделы, state machines
    algorithms.rs  (2492) — символьное исполнение алгоритмов,
                            инлайн функций
    arrays.rs      (1865) — развёртка массивов в скаляры
    names.rs       (1618) — разрешение имён, const_eval
    connections.rs        — connect: потенциалы/потоки/stream
    mod.rs         (1397) — оркестровка, settle_sizes, MAX_DEPTH=32
  check.rs         (1550) — верификация плоской модели

oxidelica-sim (~6 500 строк)
  compile.rs       (2355) — сопоставление уравнений с неизвестными
                            (аугментация путей), Pantelides с dummy
                            derivatives, tearing, BLT-подобный план
  code.rs           (740) — байткод выражений
  walk.rs           (534) — интерпретатор тел функций, которые
                            не заинлайнились
  events.rs, solvers/ (dopri45, bdf, rk4), linear.rs, symbolic.rs

oxidelica-cli, oxidelica-ide — обвязка и GUI
```

Ключевые архитектурные решения и их последствия:

| Решение                                                | Выгода                                       | Цена                                                                                                                                |
| ------------------------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Всё - скаляры: массивы разворачиваются при флэттенинге | простой бэкенд, нет тензорного IR            | взрыв размера (Spice3: 8.5M разрешений выражений, 83х повторной работы — см. EXPANSION.md), `MAX_DEPTH=32` как предохранитель       |
| Функции инлайнятся в место вызова                      | сквозное дифференцирование, свёртка констант | Media/Spice3 не инлайнятся (итеративные циклы), объём растёт комбинаторно; `walk.rs` — запасной интерпретатор без дифференцирования |
| Один проход `flatten` без промежуточных IR             | мало кода                                    | нет места, где типы/размерности известны до развёртки; ошибки размеров всплывают глубоко и поздно                                   |
| `Expr::Ref(String)` — имена строками, точки внутри     | просто                                       | нет DefId/скоупов; поиск самого длинного префикса (`flat_name`), хрупкие спецслучаи inner/outer                                     |
| Нет отдельной фазы типизации                           | меньше кода                                  | `type mismatch in sample(...)`: перегрузки решаются ad hoc; Integer/Boolean-клокованные сигналы падают                              |
| Условие компонента обязано быть compile-time           | просто                                       | 34 модели: `useHeatPort`-подобные флаги, приходящие параметром, валят флэттенинг                                                    |

Что уже _хорошо_ и не требует переделки: лексер/парсер (99.4% файлов MSL
читаются), connect-семантика (потенциал/поток/stream, expandable),
наследование/redeclare, state machines, синхронные клоки (базовые),
Pantelides + dummy derivatives + tearing в симуляторе, события.

### 2.3 Важная поправка к метрике (реализована, этап 0)

`library check` считает примером всё с `.Examples.` или `.Test` в имени —
включая utility-классы, которые никто не запускает напрямую. Теперь
он печатает вторую строку: **runnable examples** — модели с
`experiment`-аннотацией или иконой `Icons.Example` (в том числе
унаследованной через шаблон). Измерено на MSL 4.1.0:

```text
example models: 767, of which 400 flatten and 80 run
runnable examples (experiment or Example icon): 640, of which 313 flatten and 77 run
```

Что это говорит. Из 127 не-runnable утилит 87 флэттенятся и только 3
запускаются — эти 84 «провала» и правда не цели, и они больше не
прячут прогресс. Но 236 runnable-моделей флэттенятся и не запускаются —
это настоящий фронт работ, и первоначальная оценка «R1+R2 — почти всё
утилиты» была преувеличением: утилиты объясняют лишь ~84 из 320
run-провалов. Пол в `library_floor.sh` теперь держит обе пары чисел
(313/77 для runnable).

## 3. Референсные реализации

### 3.1 OpenModelica (NFFrontEnd + NBackEnd)

Зрелый компилятор, ~39k коммитов, язык реализации — MetaModelica.
Фазы нового фронтенда (NFFrontEnd, по файлам):

```text
Lookup/InstNode/ClassTree — разрешение имён по DefId, дерево инстансов
NFInst                    — инстанцирование (узлы, не строки!)
NFTyping/NFTypeCheck      — ПОЛНАЯ фаза типизации: типы, размерности,
                            variability до любой развёртки
NFCeval/NFEvalFunction    — константная оценка и интерпретатор функций
NFFlatten                 — флэттенинг типизированного дерева
NFScalarize               — скаляризация ОТДЕЛЬНО и опционально
NFConnectEquations        — connect после типизации
NFSimplify/NFInline       — упрощение и инлайн как отдельные пассы
BackEnd: BLT, Pantelides, tearing, index reduction, codegen в C
```

Чему стоит научиться:

- **Типизация до развёртки.** Размерности вычисляются на типизированном
  дереве, где redeclare уже подставлен. Это убивает наши F1, F3 разом.
- **Инстанс-дерево с узлами вместо строковых имён** (NFInstNode):
  inner/outer, lookup, protected — всё локальные операции на дереве.
- **Скаляризация опциональна** (--newBackend умеет массивы насквозь):
  большие массивы не взрывают память.
- **Интерпретатор функций — часть фронтенда** (NFEvalFunction), а не
  запасной выход: константная оценка функции = вызов интерпретатора.

### 3.2 rumoca (CogniPilot)

Rust, активная разработка, цель — «Modelica как семантический фронтенд»
для symbolic ecosystems. Явные фазы, каждая — свой crate:

```text
rumoca-phase-parse        → AST
rumoca-phase-resolve      → DefId, скоупы, разрешение имён
rumoca-phase-typecheck    → типы, размерности, structural parameters
rumoca-phase-instantiate  → extends/модификаторы
rumoca-phase-flatten      → иерархия, connect, residual equations
rumoca-phase-dae          → классификация переменных, DAE
rumoca-phase-structural   → BLT, incidence/matching, план инициализации
rumoca-sim-core           → IC solving + интеграция (+diffsol)
rumoca-phase-codegen      → Jinja-шаблоны (CasADi, JAX, ...)
```

Чему стоит научиться:

- **Отдельный resolve-пасс с DefId** до всего остального.
- **IR-границы между фазами** (rumoca-ir-ast/flat/dae/solve): каждую
  фазу можно тестировать в изоляции, есть msl-parity gate в CI.
- **План инициализации как отдельный артефакт** (IC plan) — наши R5/R6
  лечатся именно так.
- **Контрактные тесты по спецификации** (rumoca-contracts, SPEC-гейты).

### 3.3 Где oxidelica уже сильнее

- Ноль зависимостей, один бинарник, скорость сборки.
- State machines и синхронные клоки — у rumoca этого почти нет.
- Stream-коннекторы, expandable connectors — полные.
- Встроенный IDE с диаграммами.
- Проза-документация и покрытие 95%.

## 4. План устранения

Порядок выбран так, чтобы каждый этап был самостоятельно ценным, а
поздние этапы дешевели от ранних. Оценки в моделях — по реестру §2.

### Этап 0. Честная метрика (день)

- `library check`: отдельный счётчик «runnable» (experiment-аннотация
  или extends Icons.Example). R1/R2 перестают маскировать реальный
  прогресс. Ожидание: знаменатель run-метрики станет ~432-500.

### Этап 1. Быстрые победы во флэттенинге (дни) — сделано

1. **F12**: многоиндексный comprehension `{e for i in a, j in b}` — +2.
2. **F9**: `when` отдаёт целый массив (`y = u` между векторами) — +1.
3. **F5-часть**: `sample(u)` с одним аргументом — **+10 flatten, +9 run**.
   Оказался не «типовой диспетчеризацией», а двумя операторами под одним
   именем: событийный `sample(start, interval)` (Boolean) и синхронный
   `sample(u)` из 16.3 (тип аргумента, клок из уравнения).
4. **F7-остаток**: правка на одну строку работает, но прогон библиотеки
   вырос с 3.5 до 21 минуты при нуле выигранных моделей — восемь
   Spice3-моделей упираются дальше в функцию, которую нечем заинлайнить.
   **Откачено до этапа 4.**

Итог: 400/80 → **413/89**; runnable 313/77 → **326/86**.
Новое, что вскрылось: 11 моделей Digital индексируют таблицу
дискретной переменной (`NotTable[x]`) — это F1/F3, ждёт этапа 3.

### Этап 2. Resolve-пасс и DefId (1-2 недели, фундамент)

Вводится новый промежуточный слой между парсером и флэттенингом:

- Дерево скоупов, каждое имя получает DefId (индекс, не строка).
- inner/outer, imports, protected решаются здесь один раз (F8, часть
  «unknown variable»).
- `Expr::Ref(String)` → `Expr::Ref(DefId)` на выходе пасса (совместимо:
  строка остаётся для сообщений).

Это самая большая инвестиция, но она устраняет целый класс хрупкости
(поиски по префиксу имени, спецобработка `a.b.c` в flat_name) и
открывает этап 3.

### Этап 3. Типизация и размерности до развёртки (1-2 недели)

- Пасс по типизированному инстанс-дереву: у каждого компонента известны
  тип, размерности (числами), variability — ДО скаляризации.
- Redeclare/replaceable Medium подставляются до вычисления размеров.
- Закрывает **F1 (~50), F3 (34), большинство F2 (34)** — условие
  компонента вычисляется на типизированном дереве, где параметры
  инстанса уже подставлены.

Ожидание: +80-110 flatten. Это самый прибыльный этап.

### Этап 4. Функции: интерпретатор как первоклассный гражданин (неделя)

- walk.rs повышается до NFEvalFunction-подобного: records на входе и
  выходе, массивы переменной длины, while — и вызывается из const_eval.
- Инлайн становится оптимизацией, а не необходимостью: функция, которую
  не заинлайнили, всё ещё считается при инициализации и в рантайме.
- Общие подвыражения при инлайне (мемоизация разрешений — 83х повтор
  в Spice3) снимает F4 без поднятия MAX_DEPTH.
- Закрывает **F4 (32), F6 (25), часть F10/F11**.

Ожидание: +50-60 flatten (Media.Water, Spice3, Fluid).

### Этап 5. Инициализация как отдельный план (неделя)

- Отдельная система: initial equations + fixed start + гомотопия.
- Политика конфликтов (`fixed=true` против уравнения) по спецификации.
- Закрывает **R5 (7), R6 (~10)**, улучшает R3/R7.

### Этап 6. Клоки через границы и мультираздельные балансы (неделя)

- Распространение клоков по инстанс-дереву (после этапа 2 — дёшево),
  а не по плоским именам: redeclare-подкомпоненты получают клок (F5).
- Межраздельное чтение: `backSample`/`shiftSample` читают значение
  предыдущего тика источника — раздел-потребитель получает уравнение
  через `previous`-семантику (R4).

Ожидание: +15-25 (flatten + run).

### Этап 7. Численный бэкенд (по потребности)

- Алиас-элиминация до сопоставления (v = p.v - n.v цепочки) — уменьшает
  системы, лечит часть R3.
- Line search / Levenberg-Marquardt в Newton для R7.
- external "C" таблицы: реализовать `ModelicaStandardTables_*` нативно
  (сплайны, периодическая экстраполяция) — F10/F11.

## 5. Принципы миграции

1. **Ни одного большого переписывания.** Каждый этап — серия коммитов,
   каждый проходит `preflight` и не роняет текущие 400/80.
2. **Строки остаются в сообщениях об ошибках** — DefId только внутри.
3. **Каждый этап закрывается тестом, падающим без него** (правило
   репозитория) и прогоном library check с фиксацией цифр в коммите.
4. **Скаляризацию не трогаем** до этапа 3 включительно: бэкенд работает
